# Концепции и архитектура Git

## Концепции

Основные команды Git похожи на команды других систем управления версиями: добавление файлов, создание коммитов, сравнение изменений и просмотр истории. Однако внутри Git устроен иначе. Его основным объектом является не сам файл, а его содержимое. Данные идентифицируются с помощью длинных шестнадцатеричных хешей, которые зависят от содержимого объектов. Если содержимое изменяется, изменяется и его идентификатор.

## Особенности дизайна

Git создавался для разработки ядра Linux, поэтому он должен был эффективно поддерживать большое количество разработчиков и распределённую работу. Основные особенности Git:

- разработчики могут работать независимо и без постоянного подключения к центральному серверу.
- каждый репозиторий содержит полную историю проекта.
- большинство операций выполняется локально и быстро.
- хеши помогают проверять целостность объектов.
- изменения сохраняются вместе с информацией об авторе.
- коммиты выполняются атомарно: сохраняется либо весь набор изменений, либо ничего.
- поддерживаются параллельные ветки и их объединение.
- Git распространяется по свободной лицензии GPLv2.

## Репозитории

Git-репозиторий - это база данных, содержащая файлы проекта, его историю и служебную информацию. После выполнения:

```bash
git init
```

внутри проекта появляется каталог `.git`, в котором находится сам репозиторий. В нём хранятся:

- объекты Git.
- история коммитов.
- ветки и ссылки.
- индекс.
- настройки репозитория.

Локальные настройки находятся в файле:

```text
.git/config
```

Например, там могут храниться имя и электронная почта автора. При клонировании репозитория локальная конфигурация исходного репозитория не копируется автоматически.

## Объекты и индекс

### Объекты Git

Git хранит четыре основных типа объектов.

**Blob** содержит только содержимое файла. Он не хранит имя файла или его путь.

**Tree** описывает структуру проекта. Он связывает имена и пути файлов с blob-объектами, а также может содержать ссылки на другие деревья.

**Commit** описывает сохранённое состояние проекта. Он содержит метаданные, ссылку на дерево проекта и ссылку на предыдущий коммит или несколько предыдущих коммитов.

**Tag** присваивает понятное человеку имя определённому объекту, обычно коммиту.

### Index

**Index**, или staging area, содержит состояние проекта, которое будет сохранено в следующем коммите.

Когда выполняется команда:

```bash
git add <file>
```

текущее состояние файла добавляется в индекс. После этого команда `git commit` создаёт новый коммит на основе подготовленного состояния.

## Содержимое и пути файлов

Git отслеживает прежде всего содержимое файлов, а не их имена. Blob хранит только содержимое. Имя файла, путь и структура каталогов хранятся отдельно в объектах tree. Если два файла имеют одинаковое содержимое, Git может использовать для них один и тот же blob. После изменения содержимого создаётся новый объект с другим идентификатором. Благодаря этому Git может определять перемещение или переименование файла, сравнивая его содержимое, даже если имя или путь изменились. Один коммит может включать логически связанные изменения сразу в нескольких файлах:

```bash
git add file1
git add file2
git add file3
git commit -s -m "Fix application error"
```

Все подготовленные изменения сохраняются как единый коммит.

## Коммит и публикация

Коммит и публикация изменений - разные операции.

**Коммит** сохраняет изменения в локальном репозитории:

```bash
git commit -m "Made some changes in UI"
```

Для создания коммита не требуется интернет. Разработчик может создавать, исправлять и переупорядочивать локальные коммиты до их публикации.

**Публикация** делает коммиты доступными другим разработчикам. Обычно для этого изменения отправляют в другой репозиторий, например командой `git push`. Таким образом:

```text
commit - локальное сохранение изменений.
publication - передача изменений другим участникам.
```

## Upstream и downstream

**Upstream** - репозиторий, в который передаются изменения или из которого проект получает основные обновления.

**Downstream** - репозиторий, основанный на upstream-репозитории и получающий изменения от него.

Эти понятия относительны. Один репозиторий может одновременно быть:

- downstream по отношению к основному проекту.
- upstream по отношению к другому репозиторию.

В самом Git нет обязательного разделения на сервер и клиент. Роли upstream и downstream определяются организацией работы проекта.

## Форки

Fork - отдельная копия проекта, развитие которой может пойти в другом направлении. Технически каждый клон Git-репозитория является независимой копией, но обычно словом `fork` называют копию, созданную для самостоятельной разработки. Причинами создания форка могут быть:

- другое направление развития проекта.
- разногласия между разработчиками.
- лицензионные ограничения.
- отсутствие активности со стороны владельцев исходного проекта.

Fork отличается от обычной ветки:

- ветка существует внутри одного репозитория.
- fork является отдельным репозиторием.

Благодаря возможностям слияния изменения из форка позднее можно вернуть в исходный проект.

## Что важно запомнить

1. Git хранит данные в виде объектов, определяемых их содержимым.
2. Blob содержит содержимое файла, а tree - его имя и расположение.
3. Commit представляет сохранённое состояние всего проекта.
4. Index содержит изменения, подготовленные для следующего коммита.
5. Каждый Git-репозиторий может хранить полную историю проекта.
6. Коммит создаётся локально и не требует подключения к интернету.
7. Публикация изменений выполняется отдельно от создания коммита.
8. Upstream и downstream описывают направление обмена изменениями между репозиториями.
9. Ветка находится внутри репозитория, а fork является отдельным репозиторием.
